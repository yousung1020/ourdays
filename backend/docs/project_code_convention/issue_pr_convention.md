# Issue & PR Convention

## 목적과 원칙

`.github/ISSUE_TEMPLATE/`와 `.github/PULL_REQUEST_TEMPLATE.md`가 섹션 구조를 정하고, 이 문서는 섹션 안에 무엇을 쓰는지만 정한다. 템플릿 본문을 복사하지 않는다. 작성자가 사람이든 AI든 같은 규칙을 따른다. 템플릿의 섹션 이름이 프로젝트마다 다르면 아래 이름을 프로젝트 템플릿에 맞게 바꾼다.

- 템플릿의 섹션을 삭제하거나 순서를 바꾸지 않고 새 최상위 섹션을 만들지 않는다. 해당하지 않으면 "해당 없음"이라고 쓴다. 템플릿에 없는 세부 구분은 `###` 소제목으로 한다.
- 확인한 사실(코드, 실행 결과)과 추정을 구분한다. 실행하지 않은 것을 통과로 쓰지 않고, 모르는 것은 "미확인"으로 쓴다.
- AI 작성 표식, 과장 표현, 비밀값(토큰, 비밀번호, 실제 `.env` 값)을 쓰지 않는다. 자동으로 붙는 요약(코드 리뷰 봇 등)은 수정하지 않는다.

## 이슈

### 제목과 라벨

- 유형(Bug, Feature, Chore)에 맞는 템플릿 하나를 쓴다. 템플릿이 제목 접두사(`[Bug]`, `[Feat]`, `[Chore]`)와 라벨(`bug`, `enhancement`, `chore`)을 채우므로 바꾸지 않는다.
- 제목은 접두사 뒤에 "대상 + 동작"을 짧게 쓴다. 이슈 번호는 쓰지 않는다. 예: `[Feat] 초대 코드로 커플 연결`, `[Bug] 비공개 일정이 목록에 노출됨`, `[Chore] 백엔드 프로젝트 초기 설정`
- 이슈 하나는 목적 하나다. "그리고"로 이어지는 제목이면 이슈를 나눈다. 큰 기능은 Phase 단위 이슈를 두지 않고 검증 가능한 단위로 쪼갠다.

### 브랜치

- 브랜치는 이슈를 만든 뒤 `{유형}/#{이슈번호}-{영문-설명}`으로 만든다. 유형은 `feat`, `fix`, `chore`다. 예: `feat/#12-couple-invitation`
- 기본 브랜치에서 분기하고, 브랜치 하나에 이슈 하나만 담는다.

### 섹션 작성 규칙

템플릿의 섹션 이름이 규칙의 기준이다. 섹션은 유형별로 다음과 같다. 해당하지 않는 `###` 소제목은 지우지 않고 "해당 없음"으로 쓴다.

- Feature: 설명(`### 기대 동작`, `### 제외 범위 및 선행 조건`) / 작업 목록 / 완료 조건 / 참고 사항
- Bug: 설명 / 재현 방법(`### 환경`) / 기대 동작 / 실제 동작(`### 위치 및 예상 원인`) / 작업 목록 / 참고 사항
- Chore: 설명(`### 제외 범위 및 선행 조건`) / 작업 목록 / 완료 조건 / 참고 사항

항목별 규칙은 다음과 같다.

- 설명: 무엇을 왜 하는지 두세 문장으로 쓴다. Bug는 영향 범위(누구에게 어떤 영향)를 함께 쓴다. 동작을 바꾸지 않는 Chore는 그렇다고 쓴다.
- 기대 동작(Feature, Bug): "X하면 Y가 된다"로 쓰고 근거를 쓴다. 근거는 계약 문서의 절(예: API 명세서 5.3)이나 같은 방식으로 이미 동작하는 기존 코드다. 정책 결정이 필요한 항목은 "(정책 확정 필요)"로 표시한다.
- 제외 범위 및 선행 조건: 이미 처리된 범위, 이 이슈에서 다루지 않는 범위, 먼저 끝나야 하는 이슈(`#번호`)를 한 줄씩 쓴다. 예: "권한이 회수된 경우의 수신 차단은 이미 구현됨"
- 재현 방법, 실제 동작(Bug): 번호 순서로 쓰고, 직접 실행해 재현했는지 코드를 읽고 판단했는지를 구분한다. 로그와 응답은 비밀값을 제외하고 붙인다. 환경에는 브랜치 또는 커밋, JDK, OS, DB 등 재현에 필요한 정보만 쓴다.
- 위치 및 예상 원인(Bug): 위치는 클래스와 메서드 이름을 먼저 쓰고 줄 번호는 보조로만 쓴다. 줄 번호는 코드가 바뀌면 틀리기 때문이다. 코드로 확인한 것과 추정을 구분한다. 문제가 여럿이면 `#### 1.`, `#### 2.` 소제목으로 나누고 각각 위치, 현상, 기대 동작을 쓴다.
- 작업 목록: 체크리스트로 쓰고, 항목 하나는 검증할 수 있는 작업 하나로 한다. 구현과 그 테스트는 같은 항목에 쓰고 테스트만 따로 항목으로 만들지 않는다. 문서 변경은 코드 변경과 다른 항목으로 쓴다.
- 완료 조건(Feature, Chore): 명령이나 테스트로 확인할 수 있는 조건을 쓴다. 예: `./gradlew build` 통과. 확인하지 못하는 조건("잘 동작한다")은 쓰지 않는다.
- 참고 사항: 관련 문서 링크, 설계 메모, 관련 이슈를 쓴다.
- 핸드오프와의 관계: 이슈 본문은 범위와 완료 조건만 담고, 작업 단위 설계와 진행 상태는 핸드오프 문서에 둔다. 두 문서의 범위가 어긋나면 이슈를 먼저 고친다.

## Pull Request

템플릿의 섹션(설명, PR 유형, 주요 변경 사항, 테스트 결과, 관련 이슈 번호, 리뷰 시 참고사항, 체크리스트)을 모두 유지한다. 템플릿은 `.github/PULL_REQUEST_TEMPLATE.md`다.

- 설명: "기존에는"(문제)과 "변경 후에는"(동작) 두 부분으로 쓴다. 커밋이 단위별로 나뉘어 있으면 그 개수를 쓴다.
- PR 유형: 실제 변경 기준으로 체크한다. 테스트, 문서, 주석 변경이 있으면 해당 항목도 체크한다.
- 주요 변경 사항: 동작 하나 단위로 `### 1.`, `### 2.` 소제목을 쓴다. 파일, 클래스, 코드는 백틱으로 쓴다. squash 머지를 쓰면 커밋 해시가 대상 브랜치 이력에 남지 않으므로 해시를 쓰지 않는다.
- API 영향: 주요 변경 사항 안에 `### API 영향` 소제목을 둔다. 요청, 응답이 바뀌면 전후 예시와 응답 코드를 쓰고, 바뀌지 않으면 "변경 없음"으로 쓴다. 설정과 스키마 영향도 한 줄로 쓴다.
- 테스트 결과: 실행한 명령을 그대로 쓰고 통과, 실패, 미실행을 구분한다. 수정 전 실패를 확인했으면 쓴다. 실행하지 못한 검증은 이유와 함께 "미실행"으로 쓴다.
- 관련 이슈 번호: 기본 브랜치(`main`)로 머지하는 PR은 템플릿대로 닫을 이슈마다 `close #N`을 쓴다. 기본 브랜치가 아닌 브랜치(예: `develop`)로 머지하는 PR의 `close #N`은 이슈를 닫지 않으므로 `관련 이슈: #N`으로 쓰고 머지 후 직접 닫는다. 기본 브랜치로 가는 릴리스 PR은 닫을 이슈마다 `close #N`을 본문에 쓴다.
- 리뷰 시 참고사항: 동작 변경, 미검증 항목, 범위 밖으로 둔 것, 리뷰어가 볼 곳을 쓴다.
- 체크리스트: 실제로 한 것만 체크하고, 하지 못한 것은 체크하지 않고 이유를 병기한다.
